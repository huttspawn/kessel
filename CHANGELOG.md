## [Unreleased]

### Added

- **Ventures (8.0) and achievements** -- seven new tables. `achievements` (name, description, task count from `str.ach`), `achievement_tasks` (the per-objective lines, `str.ach` id1 256+), and `achievement_refs` (the payload's GUID ref graph in first-seen order: gating conditions, target quests, the exact NPC templates a kill task counts including dynamic-event variants, and child achievements). `ventures`, `venture_stages`, `venture_categories`, `venture_objectives` from the `lgcVentures_Prototype` singleton: type 6 = Classic (Veteran, 5 stages x Story/Exploration/Combat/General), 9 = Expert (Master, 8 stages x Exploration/Heroic Missions/High Value Targets plus expansion-era groups), 11 = the Basilisk Prototype companion venture; class index 1-8 = jedi_knight, jedi_consular, smuggler, trooper, sith_warrior, sith_inquisitor, agent, bounty_hunter. `achievement_reward_items` from `achRewardsTable_Prototype` (reward id -> points + item grants; the achievement -> reward-id link is not decoded yet). Venture/stage/category names are string refs packed as `(id2 << 32) | id1` into `gui/achievementcategories.stb`, now added to the STB allowlist. 8.0 PTS: 17 ventures (8 Classic, 8 Expert, Basilisk), 115 stages, 1,544 objectives, every objective resolving to a named achievement; 9,438 achievements, 26,359 refs. 7.9.1d live: Basilisk only (11 stages, 140 objectives). Field ids are identical across both builds. Classic/Expert gear (`itm.gen.ventures.*`, role/level-scaled tiers) is not referenced by any client object or singleton, even unfiltered: it is selected server-side.

- **`gom_reader`: type tag `0x18`** -- an embedded struct with the same wire layout as `0x09`, first seen in 8.0 singletons (`lgcVentures_Prototype`, the new `itmUpgradesPrototype`). Unsupported-tag errors now report the byte offset.

- **`kessel-discovery` examples `dump_singleton` and `dump_stb`** -- decode any prototype singleton to JSON (u64s matching an object GUID rendered as `@fqn`), and dump any STB by path substring or guessed path (for new-patch files the community hash dictionary does not know yet).

- **`relic_procs` table (#242, to the static-data ceiling)** -- classifies each relic item by its trigger (passive `proc` vs activated `onuse`) and the stat it affects (power / critical / mastery / defense / healing / absorb / alacrity / damage), from the relic FQN, joined to the granted-ability guid. Important finding: the **exact proc magnitude, duration, and internal cooldown are not in the .tor archive** -- the 16 proc-ability objects are shared across all rating tiers while the proc value scales with rating at runtime (the `str.abl.*` proc strings carry blank duration/ICD tokens, confirming it). So this answers "what kind of relic is this" deterministically; the live proc burst is client-side residual (cf. #111). The relic's *static* equipped stats are captured in `item_stats`.

- **`item_stats` table (per-item stats, closes #241)** -- each item's actual stat block, tooltip-ready: one row per (item, stat) with `item_level` / `quality` / `rating` denormalized on. Decoded from the item payload's `itmEquipModStats` field (GOM field id low32 `0xa4faffdd`, a `Map<STAT-enum, value>`; values are whole numbers stored as f32). 58,030 items, 182,511 stat rows. Validated against live worn gear -- Fearless Victor implant (rating 340: Mastery 1223 / Endurance 1450 / Power 940 / Critical 614), Rakata Force-Healer's Robe (344) and Med-Tech Vambraces all reproduce exactly. Key finding: there is **no per-item `modifierSetID`** in any payload (field `0xacec47da` absent on all 113,361 items), so item stats are the fixed `itmEquipModStats` block, not a budget computation -- the itemization tables (`item_budget_table` etc.) are for theorycrafting, not per-item display. Moddable shells carry no innate stats (theirs come from slotted mods, which are themselves items with their own `item_stats`) and correctly produce no rows.

- **`item_granted_abilities` table** -- the ability/proc an item grants when equipped, decoded from the item payload's granted-ability field (GOM field id low32 `0x2d7b8786`, a UInt64 object guid; resolved against `objects.guid`). This is the "what does this item DO" link. 3,831 items grant an ability; 535 resolve to an extracted ability with full effect text -- every legendary implant and tactical (oracle: Fearless Victor -> "Whenever you use a rage spending damage ability, your melee damage is increased by 10% for 10 seconds"), plus set-bonus abilities. The remaining 3,296 (relic procs, etc.) reference UNNAMED effect objects that the extraction whitelist drops, so their `ability_guid` is recorded but `ability_fqn`/`effect_text` are NULL -- this precisely scopes the relic-proc-text follow-up (capture the guid-referenced unnamed effect objects). Added `gom_reader::read_object_fields` (full-object field walk; decodes all 113,361 `itm.*` payloads with zero failures).

- **Item itemization tables** -- `item_rating_table` (`item_level` x `quality` -> `rating`, 2,010 rows), `item_budget_table` (`quality` x `item_level` x `permille` 0..999 -> stat budget `value`, ~800k rows), and `item_modifier_packages` (`mod_id` -> per-stat `permille` split, 3,635 rows). SWTOR item stats are computed, not stored per item: an item carries only `(base level, quality, modifierSetID)`, and these three tables turn that into numbers (`rating = item_rating_table[level][quality]`; `stat = item_budget_table[quality][level][permille]`, where the item's modifier package supplies each stat's permille index into the budget curve). Decoded from the `itmRatingTablePrototype` / `itmBudgetedAttributesPrototype` / `itmModifierPackageTablePrototype` singletons via a new typed-value GOM reader (`gom_reader`) that mirrors the reference `GomBinaryReader`/`ScriptObjectReader` grammar (variable-width number codec + inline type tags; DOM-free because the stream is self-describing). Oracle-verified: `budget[artifact][89]` reproduces the known relic magnitudes 484 and 167. The per-item link (materializing each item's own `modifierSetID` onto these tables) is a separate follow-up.

## [0.0.6] - 2026-05-29

### Added

- **Prototype-decode data tables** -- `conquest_events` (event roster: names + planets + invasion/themed kind), `conquest_schedule` (496-week conquest rotation, `week_ordinal` -> `event_ordinal` joining `conquest_events`; relative weeks, no calendar anchor), `companions` (full `npc.companion.*` roster, ~287 rows, display names + class/source category), `armor_classes` (9-class taxonomy from `cbtArmorTablePrototype`), `stat_curve_values` (raw per-level shield curve floats from `cbtShieldPerLevel`, grouped by `curve_hash`), and `gsf_crew` (Galactic Starfighter crew from `scffCrewPrototype`).

- **`discipline_talents` table** -- mechanical FQN-pattern mapping of `tal.<class>.skill.<segment>.<rest>` rows to disciplines. Closes the long-standing "discipline_abilities is way smaller than huttspawn's curated tree" gap by surfacing the talent half of the discipline tree. Per-class utility talents (`tal.<class>.skill.utility.*`) are fanned out to every combat discipline of that class -- mirrors how SWTOR exposes utility picks across all combat-tree pages. No tier_level / column coordinates: SWTOR's editorial tree layout (which talent sits at what tier on screen) is not encoded in tal.* payloads or FQNs, and was never something kessel could derive without speculating. The MAPPINGS.md "Effect Block Structure / level 68 (0x44)" example was a misread -- that byte is a stat_id followed by an f32 stat value, not a character level. Verified with direct payload inspection across brutality / decimate / dark_mending. Consumers that need editorial tier coordinates layer them on top of `discipline_talents` from a separate curated source.

- **Class-shared and utility ability fan-out in `discipline_abilities`** -- closes the ~451-row gap where bare `abl.<class>.<name>` rows (Saber Reflect, Force Leap, Awe, Blade Storm, Dispatch, Force Charge, Smash, Sweeping Slash, etc.) were extracted into the `objects` table but never linked to any discipline. Now each is fanned out to every combat discipline of its class with `slot_type = 'class_shared'`. Utility abilities (`abl.<class>.skill.utility.<name>`, e.g. Thwart) get the same treatment with `slot_type = 'utility'`. discipline_abilities total grew 1,133 -> 4,829 across 8 player classes x ~6 disciplines.

- **`backfill_missing_string_ids` post-extraction pass** -- recovers `string_id` linkages for canonical `abl.*` rows whose GOM payload doesn't carry a string-table type marker (so neither the FQN-based nor type-marker-based extractors at construction time could find the linkage). Strategy: derive expected display name from FQN's last segment (snake_case -> Title Case), look up STB strings whose text matches at id1=0 AND that have a description at id1=1, only commit when exactly one unused candidate remains. Fixes the canonical examples `abl.smuggler.skill.saboteur.sabotage`, `abl.trooper.skill.assault_specialist.mag_bolt`, `abl.sith_inquisitor.skill.corruption.mods.tier1.fueled_corruption`. Backfills ~14 rows in a 7.8.1.c extraction; conservative by design (id1=1-description filter rules out homonym/UI-label false positives).

### Changed

- **Identity model: `objects` PK is now `game_id` (compound, restored), not raw `guid`.** Three-id model:
  - `game_id` PK = `sha256(fqn:guid)[0:16]` -- unique per object-instance per extraction. Every junction table's `*_game_id` column targets this. Restored to the original compound formula; an earlier change had stripped the GUID component, which conflated identity (FQN-derived, stable) with change-signal (GUID, shifts on patch) into one column. Splitting them is the design intent: see `stable_id`/`payload_hash` below.
  - `stable_id` (new column) = `sha256(fqn)[0:16]` -- stable across patches, unique only post-`mark_canonical_by_fqn`. Cross-version delta joins use `USING (stable_id)` to find the same logical object across two extractions even when GUID has shifted.
  - `payload_hash` (new column) = `sha256(payload_bytes)[0:16]` -- not an identity, just a change detector. `WHERE old.payload_hash != new.payload_hash` after joining on `stable_id` surfaces "this object's data changed" for per-column delta queries.
  - `guid` is demoted to a regular column (still useful as the per-extraction change-signal alongside `payload_hash`).
  - Every junction table (`quest_chain`, `discipline_abilities`, `ability_stats`, `talent_details`, `gsf_talent_stats`, `gsf_ability_stats`) declares `FOREIGN KEY (*_game_id) REFERENCES objects(game_id)`. `talent_abilities.ability_game_id` is intentionally not FK'd because some refs point at abilities not in the objects set. SQLite enforces FKs only when `PRAGMA foreign_keys = ON` per connection -- declarations are documentation by default.
  - **Consumer impact:** every `game_id` value changes (compound differs from the FQN-only version). Icon CDN names change. Huttspawn's `computeGameId()` must hash `${fqn}:${guid}` to match.

- **Soft dedup: inferior FQN variants are no longer DELETE'd.** Replaced `dedup_objects_by_fqn` (which DELETE'd losers) with `mark_canonical_by_fqn` (UPDATE sets `is_canonical = 1` on the best row per FQN, `0` on the rest). Same quality heuristic (non-NULL string_id, then non-NULL icon_name, then larger json, then guid ASC). Inferior variants stay queryable for delta tooling and forensics. Default consumer queries should filter `WHERE is_canonical = 1`; the typed views (`quests`, `phases`, `abilities`, `items`, `npcs`) already do.

- **Stat tables now ship plain decoded data, not raw hex IDs.** `gsf_talent_stats`, `gsf_ability_stats`, and `ability_stats.raw_props` previously emitted raw `stat_id` (u8) / `prop_id` (u16) bytes that consumers had to look up against a hex dictionary to interpret. They now ship plain-English `label` and `unit` strings so consumers query e.g. `WHERE label = 'cooldown_delta_seconds'` instead of `WHERE stat_id = 0x40`. Verified anchors land with `confidence = 'verified'`; cross-referenced-but-unverified ones are `confidence = 'guess'`; everything else gets a synthesised `unknown_0x<id>` label with `confidence = 'unknown'` so the row is still queryable. The dictionary is maintained at `gsf_stat_dictionary.toml` (compile-time embedded). Schema additions: `label TEXT`, `unit TEXT`, `rank INTEGER`, `confidence TEXT` columns on both GSF stat tables (raw `stat_id`/`prop_id` retained for forensics). `rank` preserves rank-progression ordering for talents like `engine_power_regen.upgrade` whose payload encodes +4/+8/+12 as three records of the same stat. `ability_stats.raw_props` JSON keys re-keyed from hex (`"0x041f"`) to plain (`"melee_range_meters"`).

### Removed

- **Schema cleanup -- 8 redundant/dead tables dropped** for clean consumer data. `quest_rewards` (an exact subset of `mission_rewards`; use `mission_rewards` and filter `mission_fqn LIKE 'qst.%'`). `item_schema_details` (its only unique columns `binding`/`stack_size_max` were 100% NULL, and `rarity` was a verbatim copy of `item_details.rarity`; use `item_details`). `talent_effects` (never populated; superseded by `talent_stat_effects`). `meta` (unwired empty key/value table). Four never-populated foundation placeholders: `creatures`, `appearances`, `class_specs`, `ability_details`. No data loss -- every dropped table was either empty or duplicated a live table. (`appearance_specs`, `npc_details`, `schematic_details`, `talent_details`, `talent_stat_effects` are unaffected.)

### Added

- Imperial Agent and boss/op `epp.*` namespaces now extract. Two corrections to the original `epp.*` whitelist (#57): (1) IA's class prefix in source is `agent`, not `imperial_agent` -- mirrors the convention `populate_disciplines` already uses (`abl.agent.skill.*` -> `class_code = "agent"`). (2) Added `epp.companion.*`, `epp.flashpoint.*`, `epp.operation.*`, `epp.qtr.*`, `epp.daily_area.*`, `epp.exp.*` to surface boss-encounter and ops-guide choreography data the ground EPIC needs. ~9,300 new objects: 265 IA + 945 companion + 1040 flashpoint + 2265 operation (across iokath/dxun/oricon/deepstation/etc) + 1861 qtr + 522 daily_area + 2439 exp. Other epp.* namespaces (npc internals, world VFX, test fixtures) remain filtered.

- Player-class `epp.*` ability prototypes now extract (#57). The `should_extract_object` prefix whitelist accepts `epp` scoped to two namespaces: `epp.<class>.*` for the eight player classes (sith_warrior/inquisitor, jedi_knight/consular, bounty_hunter, imperial_agent, smuggler, trooper) plus `epp.flurry.{melee,ranged}.*` for shared melee/ranged mechanics. ~2,100 new objects total. Surfaces fundamental player abilities -- most visibly Saber Strike -- that have no `abl.*` counterpart in the binary because the canonical Saber Strike object lives at `epp.sith_inquisitor.prototype2.saber_strike` (and `epp.flurry.melee.<class>.saber_strike_real` for the melee mechanic). The remaining ~15K `epp.*` objects (NPC ability internals, world VFX, boss encounter scripts) stay filtered out -- huttspawn doesn't need them and they'd dominate the table. Limitation: `epp.*` payloads don't carry the `CE` string-table type marker that anchors `extract_string_id_via_type_marker`, so these rows have NULL `string_id`. Display names live at `str.abl.0.<id>` (e.g. `str.abl.0.220604` = "Saber Strike") and consumers must join on FQN convention until an `abl_string_id_overrides.toml` ships separately.

NOTE on issue #57's original framing: the issue claimed Saber Strike "lives in `.node` prototype files." That premise was wrong. NODE files contain ONLY `cnv.*` (conversation) FQNs (verified by surveying all 10,735 NODE entries -- zero header-FQN or payload-substring matches for any non-conversation prefix). The actual gap was the `epp.*` filter, fixed here.

### Fixed

- PBUK footer-chain skip recovery (#77 follow-up). The footer chain in `parse_object_dblb` occasionally jumps over a real object entirely (the chained next-size lands the cursor past an object boundary) instead of producing the off-by-N alignment that walkback handles. Added a recovery pass that scans the buffer for `01 02 <FQN>` markers after the main loop completes; any FQN we haven't already produced gets re-parsed from `marker - 42` (its true header offset). Recovers 5 more GSF talent tier FQNs (`missile_sentry_drone.tier3`, `seeker_mine.tier4a`, `seismic_mine.tier4a`, `interdiction_missiles.tier_5b`, `distortion_field.tier2`) that the prior walkback fix didn't reach, plus ~310 more objects across other categories. Total objects now 301K (vs 299K before this fix). The remaining 11 FQNs from huttspawn's GSF correction list (sabotage_probe whole namespace, ion_cannon tier_4a/5a/5b, rocket_pod.tier_5b) return zero raw-byte hits across all 806K archive entries -- huttspawn's expected FQNs literally don't exist in source data and are likely typos or legacy names.

- PBUK object boundary detection (#77). A subset of objects (~50 GSF talents and many others, ~34K total) has a variable-length preamble shorter than the assumed 42 bytes. The footer-chain offset overshoots by 1-7 bytes for these objects, which made the parser read the FQN at the wrong start (e.g. `spvp.engine.barrel_roll.tier1` instead of `tal.spvp.engine.barrel_roll.tier1`) AND read the GUID from the wrong header bytes (producing patterned non-GUIDs like `00320054000FE000` that collided with unrelated objects' real GUIDs). Truncated FQNs failed `should_extract_object`'s prefix whitelist; even after a partial walkback fix, the GUID-collided objects were silently dropped by `ON CONFLICT(guid)`. The new fix walks back through the contiguous ASCII-FQN run to find the real FQN start AND shifts the object slice backward by the same amount so the GUID/header bytes come from the right position. Recovers 39 of huttspawn's 55 expected GSF talent tier FQNs (the remaining 16 are absent from PBUK source entirely -- likely live in `.node` prototypes per #57). Side benefit: total object count rises from 264K to 299K (+34K) as the same bug affected items, NPCs, and other categories.

- `ability_stats.resource_pool` now distinguishes Galactic Starfighter (`abl.spvp.*`) from on-rails Space Combat (`abl.space_combat.*`). GSF abilities now resolve to `resource_pool='gsf'` instead of NULL — the tag identifies the game mode (GSF uses a 3-pool blaster/engine/shield system that doesn't fit a single pool name). Doc copy across `db.rs`, `docs/schema.md`, and `CHANGELOG.md` previously conflated the two; they are distinct game modes and distinct FQN namespaces.

- `ability_stats` extraction switched from a brute-force `[u16][f32]` byte scan to a sentinel-anchored prop-block walker (#74). The dominant ability template (~86% of `abl.*`, 2,891 rows) writes its property table as a contiguous run of 6-byte records starting at `01 04 00 00 80 BF` (= 0x0401 = -1.0, an uninit marker) and ending where the next 2 bytes are not in the 0x04xx range. Walking only that block eliminates the false positives the v1 brute scan produced — most visibly the spurious `force_cost` values on warrior, agent, and bounty hunter abilities that happened to contain plausible 0x04xx float pairs in their effect graphs. The dropped columns (`melee_range`, `aoe_radius`, `is_gap_closer`, `is_knockback`) had inconsistent class-dependent semantics that did not warrant flat columns; the underlying values still land in `raw_props` JSON. New column `resource_pool` derived from the FQN class segment (rage / focus / force / heat / ammo / energy / NULL).

- Per-FQN extraction now keeps the highest-quality variant instead of the first-encountered. Multiple GOM objects can share an FQN across archives (canonical objects with full payload alongside stub references); the previous `HashSet`-based dedup picked whichever appeared first in archive iteration order, which produced 77% NULL string_id and 80% NULL icon_name for abilities because stubs commonly came first. `accept_variant` now scores candidates by (has string_id, has icon_name, payload size) and skips inferior ones. A `dedup_objects_by_fqn` SQL pass runs after extraction to collapse any remaining multi-GUID FQN rows down to the single best variant.

### Added

- `gsf_ability_stats` table (#78). Decodes numeric stats from `abl.spvp.*` (GSF base ability) GOM payloads. Reuses the `[u16 LE prop_id][f32 LE value]` layout that ground abilities use, but without the `01 04 00 00 80 BF` cooldown sentinel that anchors `scan_ability_props` and with records scattered across the payload rather than packed contiguously. The decoder walks every 6-byte window and emits any record whose `prop_id` high byte is `0x04` and whose value is finite, non-zero, and in `|v| in [0.01, 100_000]` (subnormal-ish and huge magnitudes are byte-alignment noise from GUID/hash bytes). One row per record with `(ability_game_id, ordinal, prop_id, value)`; consumers pivot by `prop_id`. Coverage: 112/131 abilities (85%); uncovered abilities are passive auras whose effects live on a parent activator or in script hooks. Stat-ID semantics differ from ground abilities -- verified anchors: `abl.spvp.engine.barrel_roll` -> `0x0402 = 30.0` (30s cooldown), `abl.spvp.engine.power_dive` -> `0x0402 = 15.0` (15s cooldown).

- `gsf_talent_stats` table (#80). Decodes numeric stat values from `tal.spvp.*` GOM payloads — the values huttspawn's GSF mechanic diagrams need (firing-arc degrees, tracking-penalty %, cooldown deltas, lock-on time reductions, range and radius modifiers, etc.). Records have shape `[c9 01]? <stat_id:u8> 01 04 <f32 LE>` and end at the signature `cb 19 d7 4b ?? 03`. The existing `ability_stats` extractor anchors on a sentinel (`01 04 00 00 80 BF`) that GSF talents do not carry, which is why GSF stat values were absent from spice.sqlite despite the talents themselves being present (250/350 talents = 71% coverage; the remaining 100 are flag-only effects implemented on the parent ability). One row per record with `(talent_game_id, ordinal, stat_id, value)`; `ordinal` preserves payload order so rank progressions (e.g., +4%/+8%/+12% engine power regen) and per-effect duplicates remain distinguishable. Stat-ID dictionary documented in `src/schema/gsf_talent.rs` — high-confidence mappings: 0x40 = cooldown delta seconds, 0x41 = duration extension seconds, 0x47 = engine power pool %, 0x48 = turning rate %, 0x49 = blaster damage %, 0x4b = damage to shields %, 0x4f = tracking penalty reduction %, 0x5c = lock-on time reduction %, 0x5f = firing arc degrees, 0x62 = ammo / magazine capacity %, 0x68 = sensor radius (~250m units), 0x69 = critical hit chance %.

- `talent_details` table (#70). Per-talent classification mirroring `ability_stats`: `resource_pool` (rage / focus / force / heat / ammo / energy / gsf — derived from FQN class segment, same vocabulary as ability_stats); `tier` (the FQN's last segment — `tier1` / `tier_3a` / `base` / `passive`, useful for grouping discipline-tree levels and GSF upgrade tiers); `script_hook` (length-prefixed ASCII identifier at the payload tail per vault MAPPINGS.md lines 339-365 — examples: `abl_bh_me_kolto_shot`, `spvp_reducedcooldown`, `spvp_increasedsystemsdamagechance`, `iamilitaryofficer`). ~94% of talents have a script_hook; NULL otherwise. Useful as a join key when multiple talents share the same proc hook. One row per `tal.*` object.

- `ability_stats` table (#69). Decodes ability properties from `abl.*` GOM payloads as raw `[u16 LE propId][f32 LE value]` pairs in the 0x0400-0x04FF range. Verified prop IDs land in dedicated columns: `cooldown` (0x0401), `cast_time` (0x041b), `channel_duration` (0x0406), `hard_cast_time` (0x041a), `force_cost` (0x0403), `resource_cost` (0x041e), `melee_range` (0x041f), `aoe_radius` (0x041d), `is_gap_closer` (0x0420), `is_knockback` (0x0421). All 0x04xx hits also land in `raw_props` JSON for follow-up analysis of unknowns (0x0402, 0x0404, 0x0442 hypothesized as scaling/tick values). Plausibility filters reject implausible values (cooldown > 3600s, range > 100m, etc.). Verified in-game: force_charge cd=15, force_push cd=60+knockback, snipe cast=1.5, crushing_darkness cd=15+cast=2+force=40, overload aoe=10. Vault MAPPINGS.md lines 452-531 documents the prop-ID map.

- survey_prefixes dev binary (`cargo run --bin survey_prefixes`) enumerating every distinct FQN prefix found across all bucket PBUK objects with object counts. Used to audit the hardcoded extraction whitelist in `should_extract_object`. Closes #54.
- `populate_quest_chain_fqn_order` derives story-arc chain edges from FQN structure: `qst.location.open_world.<faction>.act_N.<class>.*` chains into act_(N+1) within the same (faction, class) bucket; `qst.exp.<NN>.<planet>.world_arc.<faction>.hub_N.*` chains into hub_(N+1) within the same (exp, planet, faction) bucket. SWTOR doesn't encode story-arc progression as inter-quest GUID refs (the existing `guid_ref` extraction caps at 158 edges, mostly bonus-mission attachments) -- the ordering lives in FQN segments. `bonus.*` and `temp_*_prereq` placeholder quests are filtered. Edges land with `link_type='fqn_arc_order'` so consumers can filter derived from real GUID-ref edges.
- `schematics` and `schematic_materials` tables (#60). Each `itm.schem.*` schematic has a companion `schem.*` GOM object (the `schem` GOM kind, ~14k instances; the *separate* one from `itm.schem.*`). The schem.* payload encodes the full recipe via CF GUID refs: an output item ref + N material refs each followed by a quantity byte. Resolved FQNs are split by prefix (`itm.mat.*` -> material, anything else -> output). Recipe data was always in the extraction -- it just wasn't decoded.
- `populate_quest_chain_npc_giver` derives `npc_giver` chain edges from the conversation graph. For each pair of quests granted by conversations sharing an NPC actor, within the same cluster bucket, emit an edge. Filter by cluster prevents the cross-arc cartesian explosion. ~1,830 new edges in 7.8.1.c (quest_chain total: 548 -> 2,378). Sample: Nar Shaddaa Sith Warrior `seek_your_contact` / `distress_call` / `disrupt_negotiations` all chain to `to_kill_a_sith_lord` -- real mission flow.
- `populate_missions` extended to include achievement-as-mission rows (galactic_seasons priority objectives, dynamic_events objectives, ventures progression, conquest objectives) and bonus-stage-aware grouping. SWTOR encodes some checklist content as `ach.*` instead of qst/mpn -- those now surface as missions tagged with source = `achievement_gs` / `achievement_dynamic` / `achievement_ventures` / `conquest`. Multi-stage bonus missions (`mpn.X.bonus.Y.staged.Z.stage_N`) keep each stage as its own mission row instead of collapsing under their parent prefix. Mission count grows 3,949 -> 5,648 -- exceeds the Exarch Mission Checklists oracle (5,446).
- `conversation_alignment_events` table -- per-conversation counts of alignment-event tokens decoded from NODE bytes. Each NODE holds a `cnv.*` conversation's playback data; the PROT header carries the cnv FQN and the body carries CF GUID refs to other game objects. A single archive scan resolves every CF E0 GUID against the loaded objects table and routes by target kind:

SWTOR's mission identity is encoded as either a qst.* object OR a unique path-prefix of mpn.* phases (alliance alerts, many class-story missions, etc. live only as the latter). Closes #34. ### Fixed

- enc / spn / plc FQN prefixes added to extraction allowlist. quest_npcs was empty after every extraction because encounter objects were filtered out before populate_quest_npcs could resolve them.
- Extended quest_npcs resolution to three hops (quest -> enc -> spn -> npc). Encounter payloads contain spawn references, not NPC references directly; without the spawn-to-NPC step, encounter resolution found zero rows.
- String scanner recognises a third encoding pattern: `0xD2 0x01 <index> <len> <ASCII>` for array-element strings in encounter payloads. The previous heuristic produced truncated strings (e.g. `Gspn.location...ban` instead of the full FQN).
- mpn.* objects now classify as `kind='Phase'` (was `kind='Quest'`). Mission phases were inflating the Quest count 8x and polluting `quest_details` with phase-shaped rows that were never real missions. New `phases` view exposes them. Closes #23.
- Spawn-prefix fallback in populate_quest_npcs: encounters that reference a base spawn name (e.g. `spn.X.multi.isen`) which the engine resolves at runtime to variants (`isen_no_weapon`, `isen_captured`) now resolve to the underlying NPC via prefix-match. Closes the_devoted_ones case from #27.
- string_id type-marker decoder tries 3-byte big-endian before 4-byte little-endian. The previous LE32-first order was poisoning achievement IDs by absorbing a trailing 0x00 separator byte. Achievement string_id coverage 42% -> 99.9%; conquest objectives specifically went 0% -> 100% (687/687). No regression on quests/items/talents. Closes #37.
- docs/schema.md id1 mapping corrected: id1=0 is the canonical name, id1=1 is the description. The doc previously said id1=1 was name and id1=2 was short description, which contradicts every actual STB row. Reported by huttspawn (verified vs dark_ward / string_id 227187).

### Removed

- populate_quest_chain (PR #11's 0xCF GUID-ref hypothesis). Brute-force search confirmed quest content GUIDs are not cross-referenced statically -- the function produced zero rows on every real extraction. Closes #19. The `quest_chain` table is retained for future link mechanisms (e.g. mpn-derived edges).
